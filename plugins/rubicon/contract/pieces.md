## The coding model

All coding produces one shape: a table with one row per quotation (a passage of a document, quoted exactly), and whatever columns the question needs. The columns are chosen for each question; nothing is fixed in advance.

- A column can be free text (open coding: the coder writes a short label or description in their own words), binary (yes or no), nominal (one value from a codebook), ordinal or numeric (a rating or a count), or a document attribute carried over from the list of documents.
- Codebook coding where a quotation may carry several items is one binary column per item; where only one item is allowed, it is a single nominal column whose values are the items.
- Causal coding is a column for the cause and a column for the effect (each free text, or each from a codebook of factors), often with a column for the direction or polarity of the effect.
- Extra columns such as certainty, conviction, polarity, sentiment, or whose view or account a passage gives (the writer's own, an organisation's, or one reported of others) are added where the question needs them.

## The pieces

A workflow is a list of steps. Each step has an "id", a "kind", "inputs" (the ids of earlier steps, or "documents" for the whole corpus) and settings. Use as few steps as the question needs. Write one workflow for the whole corpus, ending in its one write step. Where the evaluator wants a trial on a few documents first, that is a way of running this workflow, which the runner does; it is not a step of the workflow.

- **sample**: chooses documents, from the documents or from one earlier sample. Settings: "where" ({document attribute: value or list of values}: only the documents the question concerns, such as one group of the people interviewed), "documents" (a fixed list of document ids, where the question names its documents and no attribute marks them), "n" (how many to draw from those; left out, all of them), "stratify_by" (a document attribute, or null). Output: a list of documents. Default: every document the question concerns, so that a codebook built from the sample holds what any of them raises; a smaller "n" only where they are too many to read in full, stratified where the question compares groups. Where the question concerns only some of the documents, every code step reads a sample that keeps only those, never "documents", so that no other document is read and every count is out of them.
- **code**: a coder model reads each document of its input (the corpus or a sample), in sections of up to about 8,000 characters, and returns rows as the coding model above describes. Settings: "prompt" (the coding prompt in full, as the coder receives it before the text), "columns" (a list of {"name", "type", "means", "values"}: type is free_text, binary, nominal, ordinal or numeric; "means" says what the column records; values lists the allowed values for nominal or ordinal, each {"name", "means", "counts", "does_not_count"}, or names a group step whose codebook supplies them as "codebook:<step id>"). Every row also carries "document" and "quote" without listing them. "second_coder": where every column has a fixed list of values (binary, or nominal or ordinal with its values), a second coder of another model family reads every document as well, and an adjudicator settles each value only one of them placed, against the text; this is the default ("second_coder" left out), and null reads once. A free-text column cannot be read twice this way, so a judgement that needs a second reading goes in a step whose columns all have fixed values. "per_document" (true or false, the default): true where the columns describe the whole document rather than passages in it, such as what kind of body a submitter is or whether a speaker saw what they describe at first hand. The coder then reads each document whole and gives one row, and each column becomes a document attribute for the steps after it, to tabulate by, to give a judge's count its base, or to sample by with "where", as if the document list recorded it; a document the coder cannot place is left blank, and its name must not be one the document list already has. "section_chars" (default 8,000) is how much the coder reads at a time: set it at or above the longest document's length to read each document whole, where a column needs the whole account, such as a short summary of each source's story; keep it short where passages are coded one by one, since a long section gives the coder more to miss. Output: a table.
- **group**: finds the items behind a free-text column of a code step's table. Settings: "key_column" (a free_text column of its input), "granularity" (headline, standard or detailed), "max_items", "direction" (column, items or none), "multi" (true or false), "assign" (true to add an "item" column to every input row, a soft recode; false for the codebook alone), "practice" (the guidance pages its model reads, below). Output: a codebook, and the "item" column where assign is true. Defaults: standard, at most 15 items, direction column, multi false. Items are found by a strong model reading every label with its quotations; past about 1,500 rows, by embeddings first.
- **tabulate**: counts a table. Settings: "by" (a list of columns of its input table, "item" where the input's rows were assigned by a group step, or document attributes), "count" ("documents", the default, or "rows"). "sparse" (true or false, the default) lists only the combinations that occur, each with its count, rather than every combination with its zeros: set it for a table most of whose combinations cannot meaningfully occur, such as causal links counted by cause and effect from one factor list, where a link nobody tells is not a finding. "paths" (true or false, the default) traces chains: the first two "by" columns are a link's two ends, such as cause and effect from one factor list, and each row is a pair where the second can be reached from the first by following one document's own coded links, directly or through others, counted by the documents whose links make it; links are never joined across documents, any further "by" columns must describe the document, and its rows are only the combinations that occur. Use it where the question is what leads to what through intermediate steps; a joined path is the coder's links put together, not a chain the source told as one, so the answer reads the links before calling a path a story. Its input may also be "documents" or a sample, to count the document list itself by its attributes. Output: a table of counts. Counting is done by code, and the answer can state only counts some tabulation holds, each written by its cell's id: a total across cells, such as documents raising an item in any way, needs a tabulation of its own.
- **judge**: applies the evaluator's rubric to the tables, for a question that asks for a verdict of worth (how well, to what extent, good enough, the right choice). The standard must come from the evaluator, or a document they point to, before any reading: never write one of your own. Settings: "source" (whose standard it is, or the document it is quoted from), "verdicts" (a list of {"name", "means"}, best first: the overall verdicts), "criteria", and "combine": "weakest" where every criterion must hold, "best" where either of two routes will do, "separate", or, where the standard says how the criteria's ratings make the overall verdict, its rules as a list, tried in order, each {"verdict", "when": {criterion id: level or list of levels}}, the last with no "when" for "otherwise"; never an average. Each criterion is {"id", "question", "kind", "levels"}, with "scale" (its own level names, best first) where the standard rates it on a scale of its own, such as good, adequate and poor, rather than on the overall verdicts; "weakest" and "best" need every criterion on the overall verdicts. Where the standard says when a criterion cannot be rated (most say nothing about it, say), write that test as a rule's level with "verdict": null, in its place in the order. A "rule" counts documents in a tabulation: "table" (a tabulate step among the inputs), "where" (the cells, as {column: value} over that tabulation's columns), optionally "base" ({document attribute: value or list} the count is out of) and "base_where" (cells of the same tabulation, where the count is out of a group the coding finds, such as those who delivered; a share "of those who did X" needs it), and levels each {"verdict", with "at_least", "at_most", "share_at_least" or "share_at_most"}, tried in order, the last with no threshold. Where the standard's levels test different things (good where most have both time and backing, adequate where most have backing at all), give each level its own "where" rather than splitting the criterion in two: each level is tested on its own cells, in order. A "stated" criterion rests on a number one of the background documents states, such as a monitoring record's count out of a total, where the measure the standard names is one the documents being coded cannot count: "document" (the background document's id), "quote" (its words holding both numbers, copied exactly as the question quotes them; you are not given the background documents themselves), "n" and "base" (the two numbers as it states them), and levels as a rule's, a share being of that base. A "reading" has a strong model weigh rows against descriptors: "rows_from" (a code step, or a group step that assigned items), optionally "where", and levels each {"verdict", "descriptor"}. Every level, and every combining rule, also says whose it is: "from": "evaluator" with "quote", the evaluator's own words it rests on, copied exactly; or "from": "proposed", where their standard does not settle it (a number they did not give, a descriptor you had to write). Proposed levels go back to the evaluator before anything is read. Give each criterion levels that leave no gap, since evidence that falls between two descriptors cannot be placed. Output: a verdict per criterion with its evidence, and an overall verdict. Where the question asks for a verdict and no standard has been given, leave judge out, stop at the tables, and say under cannot_answer that the verdict waits on the evaluator's standard, offering two or three standards in their terms without numbers.
- **write**: a strong model writes the answer from the tables and the coded rows; every number is taken from a table, and every claim points at the rows it rests on, or quotes a document exactly where a search of the documents finds the words. The writer tests its own sentences against the rows before it finishes, and a cheap model then attaches evidence to any finding still without it, or cuts the finding. Settings: "instructions" (what the answer covers, in which order), "words", "practice" (the guidance pages its model reads, below). Inputs: tabulate steps, judge steps, and code steps whose rows it quotes. Where the answer is a narrative across the rows themselves, such as one summary a source, a code step alone is enough; the answer then states no counts.

Two common routes, which you may use or not:
- Open-code a sample, group it (assign false), then code every document closed with the codebook ("codebook:<group id>"), then tabulate. For questions whose answer rests on counts or on who is silent.
- Open-code every document, group with assign true, then tabulate by "item". Cheaper; counts come out low, because an open coder names the most obvious things and stops.

Change a default only where the question or the material gives a reason, and say why.

Code only the distinctions the answer needs. A column, a value, a step or a tabulation that the question does not ask about, and that does not change a count it asks for, is left out, however natural it seems: each is filled by a cheap coder model reading one document at a time, costs accuracy on the rest, and adds a placement a reader can dispute. Where a boundary matters to the answer, such as when something happened or whose view a passage gives, settle it inside the definition of the column it bears on rather than adding a column for it.

Define every column and every value you write, as a codebook defines its codes: what it means, what counts, and where a passage near the boundary goes instead. The coder sees only your definitions, the answer prints them, and a reviewer judges every count against them, so write them so that two careful readers would code the same passage the same way.

The answer's reader may have taken no part in planning it and never have seen the tool that runs this workflow. So write whatever the answer prints or its writer follows (the definitions, a judge step's "source", a write step's "instructions") in that reader's terms: call the person who runs the analysis and writes the report the evaluator, mention the commissioner they report to only where the question says the commissioner set or agreed something, and do not name the assistant who helped plan the question or the parts of the tool.
