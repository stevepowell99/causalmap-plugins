# Process tracing in Rubicon

How process tracing maps onto a workflow: the register of predictions as column definitions fixed before any reading, matched codings for the mechanism and its rivals, and a searched-and-absent result kept apart from one never searched. It is the method whose central claim Rubicon can actually demonstrate, and the method whose most informative result, a prediction that failed, takes the most care to record.

Back to [process tracing](process-tracing.md).

## As a plan

A prediction is a value of a code step's column, defined before any document is read: a nominal column with a value for present and a value for absent, each with its `means` stating what would be found and where, its `counts`/`does_not_count` setting the standard a trace has to meet, and where a near miss goes instead; a binary column serves where no near miss needs its own definition. The workflow's designer writes this register as part of the workflow put to the evaluator, who reads it, and any later tightening, before any document is read; a prediction written from what turned up in the material, rather than from the mechanism and the rivals alone, is exactly the ordering fault the method exists to rule out, so the register stands before the sample is read.

Each prediction, and each rival's prediction, gets its own code step over the same sample of documents, with the same section size and the same model, so that a thin search of a rival does not inflate the mechanism's case by default. Several closed columns sharing one read of a document are not yet measured for whether the coder still applies each one well, so a mechanism with four predictions and two rivals runs as six code steps, each reading every document in the sample once. Since each step's one column carries fixed values, a second coder of another model family reads the same documents too, and a value only one of them places goes to an adjudicator who reads the whole document with the definitions and rules whether it is there; a ruling that fails stands as the first coder had it, counted as unruled rather than upheld.

Tabulating each prediction's column states the count for present and for absent out of the documents the sample read, so an absent prediction is reported with its base rather than left out; a document outside the sample never enters either count. The distinction the method asks for, between never searched and searched-and-absent, rests on the sample step's document list being the base rather than the corpus.

Weighing the tabulated counts into a verdict on the mechanism is the write step's synthesis: every claim about a prediction points at the rows that carry it or at the tabulation cell stating its count. Where the evaluator wants the likelihood-ratio version, the counts are the input and the multiplication is written out in the answer's own words, with the independence of the evidence named rather than assumed, since two quotes from the same office are one piece of evidence and nothing in the record says so on its own.

The review built into the write step checks the draft against the tables, the rows and the text around every quotation it cites, including whether it states the strongest evidence against its own conclusion and says what would have changed it, which the method calls for as a matter of course; the trail that follows marks any sentence of the answer that cannot be tied to a count, a row or a quotation. A trial on a handful of documents, run before the register is spent on the whole sample, is where a prediction written too vaguely to code consistently gets caught cheaply.
