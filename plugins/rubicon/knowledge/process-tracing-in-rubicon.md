# Process tracing in Rubicon

How process tracing maps onto a workflow: the register of predictions as column definitions fixed before any reading, matched codings for the mechanism and its rivals, and a searched-and-absent result kept apart from one never searched. A workflow written before the reading can show the method's central claim, that the predictions came first, and its most informative result, a prediction that failed, takes the most care to record.

Back to [process tracing](process-tracing.md).

## As a plan

A prediction is a column of a code step set `per_document`, defined before any document is read: the coder reads each document whole and gives it one value, present or absent, nominal where a near miss needs a value of its own and binary where it does not, each value with what would be found and where, what counts and what does not as a trace meeting the standard, and where a near miss goes instead. Coding passages instead would leave absence uncodable, since every row carries a quotation. The evaluator reads this register, and any later tightening, before any document is read. A prediction written from what turned up in the material, rather than from the mechanism and the rivals alone, is exactly the ordering fault the method exists to rule out, so the register stands before the sample is read.

Each prediction, and each rival's prediction, gets its own column, coded over the same sample of documents in the same code step or a matched one, each document read whole, so that a thinner search of a rival does not inflate the mechanism's case by default. A column with fixed values is read by a second coder of another model family as well, by default, and an adjudicator rules each value only one of them placed, so every prediction and every rival gets the same second reading. Write each definition tightly enough that another careful coder would place the same document the same way; where closeness matters, a column of its own records how clearly each document shows the trace, and a tabulation split by it says how many placements were close.

Tabulating each prediction's column gives the count for present and for absent out of the documents the sample read, so an absent prediction is reported with its base rather than left out; a document outside the sample never enters either count. The distinction the method asks for, between never searched and searched-and-absent, rests on the sample's document list being the base rather than the corpus. Where the evaluator works through the plugin, the AI cites the passages itself and every document of the sample counts as read, so it names in `read_with_nothing_relevant` each document it read and found nothing in; a document it neither cited nor named there is listed, and is not a searched-and-absent result.

Weighing the tabulated counts into a verdict on the mechanism is the write step's synthesis: every claim about a prediction points at the rows that carry it or at the tabulation cell stating its count. Where the evaluator states in advance what passing and failing each test means, a judge step can apply that by rule, such as the mechanism failing where a hoop prediction is present in no document, and reports for each rule how many documents coded the other way would change its result. Where the evaluator wants the likelihood-ratio version, the counts are the input and the reasoning is written out in the answer's own words, with the independence of the evidence named rather than assumed, since two quotes from the same office are one piece of evidence and nothing in the counts says so on its own. The answer states the strongest evidence against its own conclusion and what would have changed it, as the method calls for, and it is a draft to make sense of with the programme and the commissioner, who may know of evidence the documents lack, before it is final.

Under `cannot_answer` the workflow names what counting cannot settle: whether a trace absent from the documents would have been created and would have survived, which is a claim about the record-keeping the evaluator has to make, and any part of the mechanism whose discriminating evidence lies outside the documents read. Trying the register on a handful of documents first, as a run of its own, catches cheaply a prediction written too vaguely to code consistently. The programme or commissioner agrees the mechanism and predictions before the search, which the workflow can draft but cannot agree on their behalf. Where the evaluator works through the plugin, the run can stop once the definitions are written and a few documents coded, and again once the answer is drafted. A workflow from pieces has no pause, so there the register is agreed before the run starts.
