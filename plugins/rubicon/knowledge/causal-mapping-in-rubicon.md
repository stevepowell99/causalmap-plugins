# Causal mapping in Rubicon

Rubicon's coding records a causal claim as a row with a cause, an effect and the quote behind it, tabulates the cases behind each link, and traces paths through each case's own links; it does not draw, filter or thin a map, so a question that needs those is answered as a narrower coding rather than a bigger map.

Back to [causal mapping](causal-mapping.md), which covers the method itself.

## As a plan

Causal coding is a configuration of the coding model rather than a method of its own: a code step whose columns are a cause and an effect, each free text or nominal from a fixed or grouped list of factors, often with a third column for direction. The three kinds of question below are three ways of settling what those two columns are allowed to hold.

**A theory tested link by link.** The links are agreed before any reading, so they become the values of a nominal column, one value per link, its `means` stating what would count as evidence for it, drawn from the theory-of-change document. A code step with that single column reads every document once and writes a row wherever a passage states one of the links; a link no row ever names still gets a cell, at nought, once a tabulate step counts the column by document, because every value the column allows is a cell whether or not a row filled it. The write step states the pathway's standing straight from those cells, one line per link citing its cell, combined the way a chain combines: the least-supported link decides the pathway's overall standing, in the write step's own words, and a link whose cell counts nought is named as untested rather than folded in among the ones that were read and found wanting.

**A map over an agreed list of factors.** The factors are fixed and the links are not. A code step with two nominal columns, cause and effect, each valued from the agreed factor list, reads every document once, and every passage joining two of the factors becomes a row. A tabulate step by cause and effect together, counting documents, gives each pair's cell, the cases behind it, which is the count a drawn arrow's thickness would carry. Most pairs of factors are never linked by anybody, and a link nobody tells is not a finding, so the step sets `sparse`: it lists only the links that occur, each with its count, as an edge list rather than a grid of noughts, and a long factor list stays readable.

**Paths, traced within each source.** A tabulate step by cause and effect with `paths` set counts, for every pair of factors, the documents in whose own links the second can be reached from the first, directly or through other factors; a path is never joined from two documents' links. Its rows are the links on the path, so the answer reads whether the source told the chain as one or the coder's links merely meet, and says which. This answers "what leads to what, through what" without assembling one map from everyone's claims.

**A map in the respondents' own words.** Nothing is agreed. An open code step with one free-text column records every factor named at either end of a causal claim, a row for the cause phrase and a row for the effect phrase of each passage the coder finds, both in the one column that will be grouped, so that a factor that is only ever an effect is still found rather than left out of a vocabulary built from causes alone. The labels in that column, read with their quotations, are then grouped into a short factor vocabulary, each factor defined with what counts and the near misses that belong to another (see [clustering the labels a coding invents](clustering-labels.md)). A second, closed code step then reads every document again with two nominal columns, cause and effect, each taking its values from that vocabulary, and the result tabulates exactly as the agreed-list case above.

Where links or factors are agreed, the agreeing is done by people, often with stakeholders in drawing up a theory of change, and a workflow cannot stand in for it: it reads the agreed list from a theory-of-change document where one is among the documents, and otherwise its grouped vocabulary is a draft. A Rubicon run can stop once the definitions are written and a few documents coded, so stakeholders can agree what each factor means before everything is counted, and once the answer is drafted, which is a draft to make sense of with them before it is final.

What this does not do: draw, filter, thin or zoom a map, or combine a factor with its opposite into one (keep a `~`-marked opposite as a separate value). Say this plainly rather than offering a workaround: these stay outside what a workflow of pieces does. It does not read links already coded in Causal Map either; it codes the documents afresh.

Where part of a question is outside this, a workflow says so under `cannot_answer`, naming the part, why the pieces cannot answer it, and what should answer it instead, which is where the method page's own redirections belong: a question about the strength of an effect gets a count of how many cases state it rather than a magnitude, a question about prevalence gets a count of the cases raising something, stated as a floor rather than a percentage, and a single high-stakes link is better served by [process tracing](process-tracing.md) than by a map.
