# Causal mapping in Rubicon

Rubicon's coding records a causal claim as a row with a cause, an effect and the quote behind it, tabulates the cases behind each link, traces paths through each case's own links, and draws, filters, thins and zooms a map as steps of the workflow, so every filtered map is recounted and kept in the record.

Back to [causal mapping](causal-mapping.md), which covers the method itself.

## As a plan

Causal coding is a configuration of the coding model rather than a method of its own: a code step whose columns are a cause and an effect, each free text or nominal from a fixed or grouped list of factors. The three kinds of question below are three ways of settling what those two columns are allowed to hold.

**A theory tested link by link.** The links are agreed before any reading, so they become the values of a nominal column, one value per link, its `means` stating what would count as evidence for it, drawn from the theory-of-change document. A code step with that single column reads every document once and writes a row wherever a passage states one of the links; a link no row ever names still gets a cell, at nought, once a tabulate step counts the column by document, because every value the column allows is a cell whether or not a row filled it. The write step states the pathway's standing straight from those cells, one line per link citing its cell, combined the way a chain combines: the least-supported link decides the pathway's overall standing, in the write step's own words, and a link whose cell counts nought is named as untested rather than folded in among the ones that were read and found wanting.

**Opposites in a list of factors.** Wherever a list of factors is built for causal coding, whether agreed beforehand or grouped from the respondents' words, a factor's other pole is the same label with a leading `~`: `Employment` and `~Employment`, never a second factor `Unemployment` beside `Employment`. Each pole is its own value of the cause and effect columns, with its own `means`, so the coder codes a passage about losing work as `~Employment` and one about finding it as `Employment`. A factor whose other pole nobody would name (an event, a disease, a disaster) has no `~` partner and stays as it is. The map then draws the pair as one factor, as Causal Map's Combine Opposites filter does: the links of `~Employment` count towards `Employment`, and the drawing marks which ends were flipped. This is causal mapping's way of keeping the two poles together; a causal loop diagram does it with a sign on each link instead, over variables named positively (see [causal loop diagrams in Rubicon](causal-loop-diagrams-in-rubicon.md)). Code opposites where the documents tell change both ways, losing work and finding it, so the one box carries the evidence in both directions; leave them out for a one-way event and for anything whose other pole nobody names (see [causal mapping](causal-mapping.md)).

**Reading a map with opposites combined.** Rubicon draws every claim between two boxes as one arrow, whichever ends were flipped, as Causal Map's Together bundling does, and colour says which way round the claims were told: blue where none of an arrow's passages had that end coded at the opposite pole, purple where half did, red where all did. The tail is coloured by the cause end and the arrowhead by the effect end, so a blue tail means the factor as labelled was the cause and a red tail that its opposite was. A box's border is coloured by the share of all the link ends at it that were flipped, and an arrow's count by the average of its two ends. The caption drawn under every such map says this in fewer words; it is `CAPTION.opposites` in `rubicon_open/map-dot.js`, and a change to either wording changes both. A blue-to-blue arrow from `Employment` to `Income` and a red-to-red one tell the same link in two directions (finding work raised income; losing it cut income), and both support it; a blue-to-red arrow says the factor as labelled went with the opposite of the effect. A purple end says only that the passages behind it are mixed: some about the factor, some about its opposite. It does not say how the ends pair up, since a purple tail and a purple head can hold lost-work-lost-income stories beside found-work-found-income ones, which agree, or stories that cross, which do not; nor does it say that sources disagree, that effects cancel, or that the influence is weak, because nothing is netted (page `combine-opposites-filter`). To say any of that, open the arrow's passages and read which ends were flipped together. Causal Map's Separate bundling draws each combination of flipped ends as its own arrow, up to four between two factors (page `combine-opposites-filter`); Rubicon's maps do not offer it.

**A map over an agreed list of factors.** The factors are fixed and the links are not. A code step with two nominal columns, cause and effect, each valued from the agreed factor list, reads every document once, and every passage joining two of the factors becomes a row. A tabulate step by cause and effect together, counting documents, gives each pair's cell, the cases behind it, which is the count a drawn arrow's thickness would carry. Most pairs of factors are never linked by anybody, and a link nobody tells is not a finding, so the step sets `sparse`: it lists only the links that occur, each with its count, as an edge list rather than a grid of noughts, and a long factor list stays readable.

**Paths, traced within each source.** A tabulate step by cause and effect with `paths` set counts, for every pair of factors, the documents in whose own links the second can be reached from the first, directly or through other factors; a path is never joined from two documents' links. Its rows are the links on the path, so the answer reads whether the source told the chain as one or the coder's links merely meet, and says which. This answers "what leads to what, through what" without assembling one map from everyone's claims.

**A map in the respondents' own words.** Nothing is agreed. An open code step with one free-text column records every factor named at either end of a causal claim, a row for the cause phrase and a row for the effect phrase of each passage the coder finds, both in the one column that will be grouped, so that a factor that is only ever an effect is still found rather than left out of a vocabulary built from causes alone. The labels in that column, read with their quotations, are then grouped into a short factor vocabulary, each factor defined with what counts and the near misses that belong to another (see [clustering the labels a coding invents](clustering-labels.md)). A second, closed code step then reads every document again with two nominal columns, cause and effect, each taking its values from that vocabulary, and the result tabulates exactly as the agreed-list case above.

Where links or factors are agreed, the agreeing is done by people, often with stakeholders in drawing up a theory of change, and a workflow cannot stand in for it: it reads the agreed list from a theory-of-change document where one is among the documents, and otherwise its grouped vocabulary is a draft. A Rubicon run can stop once the definitions are written and a few documents coded, so stakeholders can agree what each factor means before everything is counted, and once the answer is drafted, which is a draft to make sense of with them before it is final.

**A filtered map.** A code step that names its cause and effect columns as its `links` can be counted by a tabulate step with `filters`, which puts those links through Causal Map's own link filters before anything is counted: tracing paths between factors, the links within so many steps of a factor, zooming hierarchical labels to fewer levels, collapsing factors into one, combining a `~` factor with its positive (which every map does by default, below tracing and above anything that renames factors, unless the step's own filters set Combine Opposites otherwise), keeping one group of documents, dropping labels or self-loops, and keeping only the more frequent links or factors. Order them as the filter-ordering rules say: tracing first, then anything that renames factors, then frequency last. Each filtered view is its own tabulate step, and the report draws it as a map whose arrows open the passages behind them. A request for another view of the map, filtered, thinned, zoomed or traced, is answered with another such step, recounted with the rest, not with a drawing made outside the workflow, which nobody could check against the record. Refiltering a map at will, trying one filter after another, is what the Rubicon page is for once a run can be opened there; until then, offer the views asked for as fixed steps, and anything else is made under the skill's rule for outputs beyond the report: labelled as exploration and kept out of it.

What this does not do: it does not read links already coded in Causal Map; it codes the documents afresh.

Where part of a question is outside this, a workflow says so under `cannot_answer`, naming the part, why the pieces cannot answer it, and what should answer it instead, which is where the method page's own redirections belong: a question about the strength of an effect gets a count of how many cases state it rather than a magnitude, a question about prevalence gets a count of the cases raising something, stated as a floor rather than a percentage, and a single high-stakes link is better served by [process tracing](process-tracing.md) than by a map.
