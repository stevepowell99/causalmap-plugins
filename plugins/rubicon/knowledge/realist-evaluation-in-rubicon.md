# Realist evaluation in Rubicon

Where the method maps onto a workflow of the six pieces (sample, code, group, tabulate, judge, write), where it does not, and what the workflow must say it cannot answer.

Back to [realist evaluation](realist-evaluation.md).

## As a plan

A CMO configuration has three parts, and what matters is which of them a source links. A code step's row names the configuration a quotation bears on (`configuration`, nominal, its values the kinds found by grouping an open coding, or stated directly where the evaluator already holds a theory) and, in three binary columns, which of its parts the passage itself states: the context, the mechanism and the outcome. A passage that ties the context to the reasoning it switched then carries both in one row, which is the strongest evidence for the link. Where a source states the parts in different passages, the configuration is read off that source's own rows together, and never from parts found in different sources, since a context one person describes and a mechanism another describes are two claims and not a configuration; the answer says which configurations rest on a passage linking the parts and which only on one account's separate passages. A document attribute carries the site or group each source belongs to. The column definitions have to carry both halves the method depends on: ask as carefully about the sites a configuration says should not show the mechanism as about the ones it says should, since a column that only looks where the theory expects confirmation cannot refute it, and separate resource from reasoning in what counts, so an activity the programme ran does not get coded as the reasoning it was meant to trigger, following the test on the [CMO page](realist-evaluation-cmo.md#a-mechanism-is-a-resource-plus-reasoning). Write each configuration's definition, and each part's, tightly enough that another careful coder would place the same passage the same way; where a placement is close, such as a passage that might describe the reasoning or might only describe the activity, the row says so and the answer reports it.

Where no configurations exist yet, an open code step drafts candidate resource-plus-reasoning-plus-outcome statements as free text, and grouping those labels into kinds finds the recurring patterns: each kind is a candidate configuration, defined by what it means, what counts, the near misses that belong to a different kind, and example quotations, which is the initial theory in a form a reader can see. Each row's kind is recorded as a nominal column; counts from an open coding are floors, since an open coder names the most obvious things and stops. Testing the theory against the rest of the corpus is a further code step whose `configuration` column takes those kinds as its values; a later revision is a further code step of its own rather than an edit to the first, so the trail shows the theory that was tested and not only the one that survived.

Tabulate counts documents by `configuration`, by the parts each states and by site: how many sites show the mechanism where the context holds and how many where it does not, and whether the outcome follows the mechanism or turns up without it, each count taken out of the sites the configuration claims to cover (`.within.` that scope) rather than out of every site read, so the base matches what the configuration asserts rather than the whole corpus. A tabulation of the outcome by site, read before any configuration exists, is the demi-regularity: the gaps and clusters it shows are what the configurations have to explain.

Judge only applies where the evaluator layers a worth question on top of the configurations, with a standard of their own. Supported, refuted and refined are readings of the tabulation against the method's own tests, not that verdict, so write states them rather than a judge step ruling them.

Write reports a configuration as supported where the mechanism and the context it depends on appear together and not apart, refuted where the mechanism or the outcome occurs without the other and nothing accounts for it, and refined where a version changed, saying what moved it and on what evidence, with every version kept as its own step rather than overwritten. Deviant sites, those with the pattern but not the outcome, or the outcome without the pattern, are named from the tabulation and read by a further code step scoped to just those documents for what the configuration is missing.

A first configuration tested on a handful of documents, agreed with the evaluator before the rest of the corpus is read, catches a configuration too vague to code or one the corpus plainly cannot speak to.

## What the workflow must say it cannot answer

- The realist interview: putting the theory to a respondent and inviting them to correct it is a conversation the evaluator conducts, not a coding pass. Material gathered any other way can fail to support a configuration and cannot refute one, because nobody in it was ever asked the question that would have let them say so.
- A further round against new or held-back material: a workflow reads one fixed set of documents, so testing a refined theory on the next round is a further workflow once that material exists.
- Retroduction: proposing a mechanism nobody has stated, from an outcome pattern alone, is a judgement about the world rather than a count or a grouping of what the documents already say.
- Middle-range theory: whether a configuration generalises beyond this programme is read against literature the corpus does not contain, which the pieces do not read, and is the evaluator's to judge.
