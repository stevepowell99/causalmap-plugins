---
name: rubicon
description: Answer an evaluator's questions from a folder of documents such as interview transcripts, leaving a workflow that code recounts, so every count in the answer is made by code and every quotation is checked against its document. Use when the user runs /rubicon or asks Rubicon to answer an evaluation question from the documents in this folder, and whenever they ask about Rubicon work already done: their runs, earlier questions or reports, as in "list my Rubicon runs", which this skill draws as one clickable page, a combined report of the answers of several runs together, or a change to a report.
argument-hint: "the evaluation question"
---

You are running Rubicon in the evaluator's own folder. Set the folder up, settle the question with the evaluator, then carry out the brief below.

Whenever the evaluator is to agree something, such as the documents, a rubric, the settled question, the definitions or a draft answer, put it in the chat itself, in your own reply, never only in a file or a tool call, because a file they have to find and open, or a tool call the app shows folded away, may never be shown to them. Once the run is started, put it in the run as well before you ask, and when they have answered, record it, naming what in the run they agreed, so the report shows what they agreed from the run itself, never from words you typed again, and says where it changed afterwards. The documents and the settled question, agreed before the run starts, are recorded once the run holds them. Where it has parts, show it as a short markdown table: a rubric as its criteria by its levels, definitions with an example passage for each, each cell a short phrase. Then ask for the decision with your tool for multiple-choice questions where you have one, otherwise as a short list of options: one question to accept it or to change a part they name, which they then say in their own words, and a question for each real choice inside it, such as a threshold or how the criteria combine, each with the option you recommend first and marked as recommended. The table carries the content and the questions carry the decisions, so never squeeze a rubric or a set of definitions into one question's options. On a change, show the table again with the change made and ask again, and go on only once they agree. Leave to choose for them settles what you choose, never the agreement: once you have chosen, put what you chose to them as above and wait for their go, even where they have said they are away.

The run is a folder, and you keep it by writing its files and running the engine's scripts on them. Run every script through `${CLAUDE_PLUGIN_ROOT}` as this skill writes it, each time, and never through a path written out earlier in the conversation: a conversation can outlive the build it began with, and an old path runs an old engine. What is to be agreed goes in it as the definitions as a code step's columns and a rubric as a judge step in `workflow.json`, or a draft answer in `answer.md`. Record each answer with `python "${CLAUDE_PLUGIN_ROOT}/engine/agree.py" <the run's folder> --what "<a few words naming what was put to them>" --about <what in the run they agreed: question, documents, answer, or a step's id> --via <"question cards" or "chat"> --answers <a JSON file in drafts/ listing each question put to them as {"question", "options", "chosen"}>`, adding `--changes "<their words>"` where they asked for a change. It keeps what the run holds of each thing named; never write `work/agreements.json` yourself.

When they ask for a change to a finished report, the report is a record of what was done, so it changes only through that record. Never edit the `.html`, `.doc` or `.zip`, and never change what the answer claims by rewriting its prose alone. First say in one sentence which of three kinds the request is, then act on it:

- **A new question**, or the same question asked of other documents, another group or by another method: not a revision. Say it is a new run, which leaves the run they have as it is, and settle it from step 4, suggesting a new chat only if this one is long.
- **Presentation**: wording that states no finding, headings, the order of sections, or removing a section the conclusions do not rest on. Edit the run's `answer.md` and nothing else. If a section to be removed holds evidence the opening conclusion or a summary relies on, it is not presentation: treat it as substantive.
- **Substantive**: anything that would change a number, a quotation, a finding, a judgement, a verdict, a headline or a summary; a request for another view of a causal map or its loops, filtered, thinned, zoomed or traced, which is a new tabulate step with `filters` over the code step that names its `links` (see `${CLAUDE_PLUGIN_ROOT}/knowledge/causal-mapping-in-rubicon.md`) and a `{{figure}}` line for it, not an output made outside the workflow (below); someone who wants to refilter a map at will is offered the views they name as fixed steps, and an interactive map as an exploration output (below); adding a section with new evidence; or changing a definition, a coding decision or the rubric. Copy the run's `recount/` to `recount-before/`, then make the change in the workflow, never only in the prose: a new or changed step in `workflow.json`, rows recoded where a definition changed, new rows coded for new evidence. Recount, then run `python "${CLAUDE_PLUGIN_ROOT}/engine/stale.py" recount-before recount answer.md`, which names every paragraph resting on a count, row or key claim that moved, every paragraph resting through `[§ ]` links on one of those, however indirectly, and the opening conclusion; read each against the new figures and rewrite it so it says only what they show, citing counts and rows as the brief requires. A rubric changed after the evidence has been read is reported as such, with the reason, because a standard set after seeing the evidence can be made to fit it. Where the run had a second reading and the coding changed or new claims were added, run it again on what changed. If a recount prints `EARLIER RUN REVISED`, a run this one builds on has been revised since: tell the evaluator in a sentence, and offer to bring this run up to date as a substantive revision, by pointing the step's `from` at the later fingerprint and recounting as above. If the change cannot be made this way, because it reaches back into how the question was settled, the sample or most of the coding, or because you cannot say which paragraphs it touches, do not patch the report: say so, and run the whole question again as a new run. A report out of step with its record is worse than a second run.

**Earlier runs.** When the evaluator asks which questions Rubicon has answered, or for an earlier run, run `python "${CLAUDE_PLUGIN_ROOT}/engine/register.py" --list --folder <the documents folder you have open, if any> --data "${CLAUDE_PLUGIN_DATA}" --out rubicon-central.html`. It writes Rubicon Central, one page listing every run in every folder Rubicon has answered from on this computer, with each report inside it: choosing a run in the list shows its report beside the list. Show it as a page. **In Cowork**, write it into the outputs folder and present it with the tool that presents files, since Outputs lists only files presented or created with your file tools, present nothing else, and open your reply with "**To see all your Rubicon work, click `rubicon-central.html` under Outputs in the panel on the right.**" Where you can make artifacts, show it as an HTML artifact; in Claude Code, link it. Hand the page over whatever it lists, even nothing: it names each run it found, including runs created before reports were sealed, and says why any run cannot be opened, so never list the runs in prose instead. Add nothing in prose that the page shows. If it lists fewer folders than they expect, as after Rubicon was reinstalled, ask which folder holds their work, run `register.py --find <that folder> --data "${CLAUDE_PLUGIN_DATA}"`, which adds every folder under it that holds Rubicon runs, then make the page again. A folder the page says it cannot reach has to be opened in this chat, or in a new one, for its runs to show. To revise a run, the evaluator opens its documents folder in a chat and asks there.

**Combined report.** When the evaluator asks for a combined report, or for the answers of several runs together in one report, such as every question answered from these documents or the ones they name, find the runs in `rubicon-runs.md` beside the documents, and where it is not clear which they mean, show the list and ask. Then run `python "${CLAUDE_PLUGIN_ROOT}/engine/bind.py" <each run's report .html, in the order they want> --date "<today's date>"`, or `--folder <the documents folder>` in place of the reports for every run there at its latest revision. Where `rubicon-plan.md` lists the runs, it takes their roles and the order of the questions from there; otherwise put `--question`, `--shared` or `--background` before a report to give it a role, as a background run is not numbered as a question. Give it `--title "<a few words>"`: the title they gave the whole, or, where they gave none, one you write from the questions as their reader would put it; without one it is titled from the parts' headings. In the hand-over, say what you called it and that another title recreates it under that title, changing nothing else. It writes a combined report beside the documents, a page and the same for Word: a cover, the questions with their short answers, each answer in turn, and every run's annex gathered at the end, each part naming the run it came from. It changes no answer and counts nothing afresh: each part is created from its run's sealed zip, and a run whose zip does not match its report, or whose counts no longer follow from its coded passages, is left out and named, which you tell them. Hand the combined report over as you would a report, the page first. A change to any answer in it is a revision of that run, as above, after which the combined report is made again.

**Reports, and anything else.** A report, in HTML, Word, PDF or any other format, is only ever made by `render_report.py` from the agreed workflow. A PDF or another format someone asks for is converted from the rendered report, never written afresh, no number or word of it changes on the way, and it keeps the report's file name, whose last eight characters are the start of the zip's fingerprint, changing only the extension, so every copy is seen to match its zip. To make a PDF yourself, print the rendered `.html` with a headless Chromium, such as Playwright's `page.pdf`; where none is available, tell them the browser's Print saves the report as a PDF. What the workflow can answer goes through it, as above, so nothing else ever stands in for a step that was asked for, such as a filtered map. Beyond that you may make any other output the evaluator asks for, and may offer one where it would help, making it only once they say yes, such as an interactive map to explore, a chart or view of their own, or an ad hoc script, as long as it opens with this banner, word for word: "Exploration only. This is not part of the checked report: it was made outside the run's workflow, nothing in it was recounted or checked, and it cannot be rebuilt from the zip." Nothing from it goes into `answer.md`, the report, the Word copy, any PDF or the zip. Say in one line that anything in it worth keeping becomes a fixed step through a substantive revision, and offer to do that.

Every revision then ends the same way. Add a line to `revisions.md` in the run's folder, creating it with the heading `# Revisions`: `- ` then the date, what was asked, what changed in the workflow, the coding and the answer, and what was recounted. Run the recount with the answer and the render as at the end of the run; the new files carry `-revision-` and a number, and the earlier report, Word copy and zip stay as they were. The run keeps its ID: leave `"run_id"` in `workflow.json` as it is. A run that began without one gets none. The new zip holds the workflow, rows, answer and revisions as they now stand, and the report lists the revisions in its account of how it was made. Run `register.py` on the new report as at the end of the run, and hand the files over as before.

The brief:

An evaluator asks: "$ARGUMENTS" The documents are in corpus/ (corpus/index.csv lists them with their metadata). Answer the question, and write your answer to answer.md. The answer opens with its conclusions, in plain sentences that answer the question; it says only as much about definitions and method as the reader needs to rely on a statement, where that statement is made. The report adds how the answer was made from your workflow and audit trail, so the answer carries no account of procedure, coding or files; where something limits how far it can be relied on, it ends with a section headed `## Limitations` holding only that. Where a sentence about method or a limitation rests on a claim about how a method works or what it can establish, cite the source the method notes give for that claim, as they give it (author, year, title, and its web address written out in plain text where the note has one, since the report does not draw markdown links), in round brackets in that sentence, since square ones cite rows; cite no source the notes do not name, no page number they do not give, and nothing where no such claim is made. The answer gives the kind of answer the question asks for. Where it asks for a judgement, it states the judgement first and gives as its reasons what the evidence in each case shows, how directly, and against what alternatives; a count of documents supports a judgement but is never its reason. Where the evidence is mixed or thin, it still gives its best judgement and says how sure it is; "unclear" qualifies a judgement and never replaces one. Where the question judges against something (aims, a plan, a standard, another group), the answer first states that reference as the documents give it, with citations, then judges against it; if the documents do not give it, say so. Work however you judge best.

Method notes are in knowledge/ (knowledge/README.md lists them); consult any that bear on the question.

As you work, keep an analyst's audit trail in work/, so that a reviewer can check the answer and another analyst can follow the same procedure:
- every script you write, and its output;
- a table recording, for each document, what it contains that bears on the question, with the quotation;
- if you use subagents, the full brief you give each one and what it returned.
When you finish, write work/procedure.md: which documents were read, by whom, under which brief, and how the results were combined into the answer, pointing to the files above. It states the procedure only, not the findings.
Your work must also be left as a workflow that code can carry out again, so that every count in your answer is recounted by code from the rows you coded, and another coder can follow your definitions and code the documents afresh. contract/pieces.md describes the steps such a workflow is written in. Use sample, code, group, tabulate, judge and claims steps. The categories you settle on yourself become the values of nominal columns, or binary columns, each defined as the file asks. A group step is for categories found in how the documents describe something, kept apart from what you expected to find and then applied the same way to every passage: you are its grouper, as you are its coder, so of its settings only "key_column" and "assign" apply, and what contract/pieces.md says of its model, its limit on rows and its "practice" pages is Rubicon's hosted service. A code step can carry any columns you find useful for the question, and its tables may count, compare and filter by any of them as the question needs. A column that follows from another of the same step, such as a broader theme for each detailed label, is defined once with "from" (that column) and "map" ({each of its values: this column's value}), and the recount fills every row from the mapping, so you never write it on the rows. Give every tabulate step a "description": one sentence saying what it counts and out of what, written for the report's reader. Leave out the settings that choose models, second coders and sections; you are the coder.
- Write workflow.json: {"question_as_agreed", "steps": [...]}, with a write step last, {"id": "answer", "kind": "write", "inputs": [the tabulate and judge steps, and the code steps whose rows you cite]}.
- For each code step, write coded/<step id>.json: a JSON list of the rows you coded, each {"document": its id in corpus/index.csv, "quote": the passage copied exactly from the document, and a value for each of the step's columns}. A link that one speaker tells as a step in a chain also carries that chain's "sequence" and its "step", as contract/pieces.md says. A per_document step has one row per document.
- A code step the evaluator agreed to build on from an earlier run answered from these documents is taken, not coded: write it as {"id": its id in that run, "kind": "code", "inputs": ["documents"], "from": {"run_id": that run's ID, "fingerprint": as rubicon-runs.md or its report gives it, "step": the same id, "take": "rows"}}, with no columns and no coded/ file. The recount takes that run's coded and checked rows from its zip, keeping their row ids, so you tabulate, judge and cite them as your own; it refuses them where a document reads differently. With "take": "definitions" only the step's columns come across, and you code the documents to them in coded/<step id>.json, as for a later wave or other documents.
- A judge step's reading criterion, one that weighs passages against each level's descriptor because it cannot be counted, is yours to read, as the coding is. Once the rows are recounted, read the rows it names in recount/rows.md against each level's descriptor and write judged/<judge step id>.json: an object of {criterion id: {"verdict": one of its levels, or "between" with "between": [the two levels] where the passages fall between two descriptors, "rows": [the ids of the rows it rests on], "against": [the ids of rows that pull the other way], "why": a sentence}}. The recount applies it beside the counted criteria and combines them as the step says.
- A group step's codebook is yours to draw, as the coding is, from a code step that coded the material openly, with a free-text column for the label in the speaker's words, each label one specific thing with its direction. Once those rows are recounted, read every distinct label in recount/rows.md with the passages under it, and write judged/<group step id>.json: {"items": [{"id": the item's name as a reader sees it in a table, "label": a fuller name, "means": a sentence, "counts": the kinds of account that belong, "does_not_count": [{"text": a near miss, "goes_to": the id of the item it belongs to, or null}], "examples": [{"row": the id of a row that shows the item plainly}], "from_labels": [every open label it gathers, written as in the rows], "from_rows": [only the ids of rows whose passage belongs here although their label is gathered elsewhere]}], "unplaced": [{"label", "reason"}], "notes": what you merged, split or left alone, and why}. Every open label goes in one item's "from_labels" or in "unplaced", and nothing that fits no item is forced into the nearest one. The recount gives every row the item its label is gathered into, and reports any label placed nowhere, placed twice, or named but carried by no row. With "assign": true, a tabulate step reading the group step counts by "item" (rows left over read "none"). For a hard recode, leave "assign" false and code the documents again in a later code step whose nominal column has "values": "codebook:<group step id>", giving each passage an item's id, or "OTHER" where it fits none.
- Tag the answer's key claims as its counts are tagged. A key claim is a finding the answer turns on that no count states, such as what is going on, how something works, why it happened, or where accounts diverge. Add one claims step before the write step, {"id": "k", "kind": "claims", "inputs": [the code steps whose rows the claims rest on]}, and code the passages each claim rests on, and those that cut against it, as you code those a count rests on. Once the rows are recounted, write judged/k.json: an object of {claim id, in lowercase letters and digits: {"says": the claim in one sentence, "rows": [the ids of every row it rests on, as recount/rows.md gives them], "against": [the ids of the rows that cut against it], "found_by": how another reader would find these passages again (the column and values that select them, or what to read for), "why": a sentence saying how the passages bear the claim out}}. In answer.md, cite each claim as [k.<claim id>] on the sentence that states it, beside the row ids that sentence rests on, never in their place: every sentence that rests on rows still cites its own rows, as below, and the tag adds the claim's passages for and against it and how they were found. Tag the claims the answer turns on and no others: a sentence that frames, links or restates needs no tag.
- Run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . This recounts your workflow from your rows, writes recount/tables.md (every cell with its id) and recount/rows.md (every row with its id), and lists in recount/report.json what it could not use: quotations not found in their document, values not among a column's defined values, faults in the workflow. Fix what it reports and run it again until the report is clear.
- In answer.md, write every count as its cell's id in braces, such as {t_base[yes]} (the step's id, then the values of the table's columns in square brackets, joined by commas; copy it exactly from recount/tables.md), which code replaces with "n of base"; do not write numbers yourself. Cite the rows a claim rests on by their ids in square brackets, as recount/rows.md gives them. Quote documents exactly. In the answer's own text, name the document in round brackets beside every quotation and every claim about what a document says, whether or not a count stands behind it; this is written into the answer and asks for no citation beyond those your counts rest on.
- Before you check the answer, reread each document for anything that bears on the question but that the answer misses or contradicts, then code it or say why it does not fit, and write work/read.json: {"nothing_relevant": [the ids of the documents you read that hold nothing bearing on the question]}, which the report lists as your word.
- Then run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . --answer answer.md and fix what its "answer" section reports.
