The brief:

An evaluator asks: "$ARGUMENTS" The documents are in corpus/ (corpus/index.csv lists them with their metadata). Answer the question, and write your answer to answer.md. The answer opens with its conclusions, in plain sentences that answer the question; it says only as much about definitions and method as the reader needs to rely on a statement, where that statement is made. The report adds how the answer was made from your workflow and audit trail, so the answer carries no account of procedure, coding or files; it ends with a section headed `## Limitations` holding only what limits how far it can be relied on. The answer gives the kind of answer the question asks for. Where it asks for a judgement, it states the judgement first and gives as its reasons what the evidence in each case shows, how directly, and against what alternatives; a count of documents supports a judgement but is never its reason. Where the evidence is mixed or thin, it still gives its best judgement and says how sure it is; "unclear" qualifies a judgement and never replaces one. Where the question judges against something (aims, a plan, a standard, another group), the answer first states that reference as the documents give it, with citations, then judges against it; if the documents do not give it, say so. Work however you judge best.

Method notes are in knowledge/ (knowledge/README.md lists them); consult any that bear on the question.

As you work, keep an analyst's audit trail in work/, so that a reviewer can check the answer and another analyst can follow the same procedure:
- every script you write, and its output;
- a table recording, for each document, what it contains that bears on the question, with the quotation;
- if you use subagents, the full brief you give each one and what it returned.
When you finish, write work/procedure.md: which documents were read, by whom, under which brief, and how the results were combined into the answer, pointing to the files above. It states the procedure only, not the findings.
Your work must also be left as a workflow that code can carry out again, so that every count in your answer is recounted by code from the rows you coded, and another coder can follow your definitions and code the documents afresh. contract/pieces.md describes the steps such a workflow is written in. Use only sample, code, tabulate and judge steps: you do the grouping yourself, so the categories you settle on become the values of nominal columns, or binary columns, each defined as the file asks. Each column's definition also says what makes a passage weak for that column, as "weak": a sentence, such as a passage that hints at a value rather than says it. Leave out the settings that choose models, second coders and sections; you are the coder.
- Write workflow.json: {"question_as_agreed", "steps": [...]}, with a write step last, {"id": "answer", "kind": "write", "inputs": [the tabulate and judge steps, and the code steps whose rows you cite]}.
- For each code step, write coded/<step id>.json: a JSON list of the rows you coded, each {"document": its id in corpus/index.csv, "quote": the passage copied exactly from the document, and a value for each of the step's columns}, adding "weak": true to a row whose passage is weak by its column's definition, so the tables count it apart from the firm rows. A link that one speaker tells as a step in a chain also carries that chain's "sequence" and its "step", as contract/pieces.md says. Mark a row weak only by the weakness its column's definition names; passages that say the same thing get the same mark. A per_document step has one row per document.
- Run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . This recounts your workflow from your rows, writes recount/tables.md (every cell with its id) and recount/rows.md (every row with its id), and lists in recount/report.json what it could not use: quotations not found in their document, values not among a column's defined values, faults in the workflow. Fix what it reports and run it again until the report is clear.
- In answer.md, write every count as its cell's id in braces, such as {t_base.c1}, which code replaces with "n of base"; do not write numbers yourself. A count is of firm rows only. The documents a cell holds only through weak rows are listed apart in the note a reader opens from the count, so the answer names them only where they change what its sentence claims, such as beside a count of none, or one they would turn from a minority into a majority; it then writes {<cell id>.weak}, which recount/tables.md gives, beside the count, never in it. Cite the rows a claim rests on by their ids in square brackets, as recount/rows.md gives them. Quote documents exactly.
- Then run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . --answer answer.md and fix what its "answer" section reports. recount/answer.resolved.md is the answer the evaluator reads.
