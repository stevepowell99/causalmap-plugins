---
name: rubicon
description: Answer an evaluator's question from a folder of documents such as interview transcripts, leaving a workflow that code recounts, so every count in the answer is made by code and every quotation is checked against its document. Use when the user runs /rubicon or asks Rubicon to answer an evaluation question from the documents in this folder.
argument-hint: "the evaluation question"
---

You are running Rubicon in the evaluator's own folder. Set the folder up, settle the question with the evaluator, then carry out the brief below.

1. Read `${CLAUDE_PLUGIN_ROOT}/about.md`: it is what Rubicon says about itself, and what you say about Rubicon comes from it. The question is the text after the command: "$ARGUMENTS". If it is empty, or asks about Rubicon itself (what it does, how to use it) rather than about the documents, answer from that page, say that they run it by opening the folder of their documents, or attaching the documents to the conversation, and typing `/rubicon` followed by their evaluation question, then stop. Otherwise open, before anything else, with Rubicon's opening card, `${CLAUDE_PLUGIN_ROOT}/opening.html`, shown exactly as written apart from three fillings: `{{question}}` with the question as typed, `{{material}}` with what you can tell of the documents without reading them (how many, what kind of file, any spreadsheet beside them; "none yet" if there are none), and `{{model}}` with the model you are running on, as step 2 finds it. Escape `&`, `<` and `>` in what you fill in. Where you can make artifacts, show the filled card as an HTML artifact; in Claude Code, which shows text only, give the card's words as formatted text, the same words in the same order with its headings in bold; otherwise save it as `rubicon-opening.html` where the user can open it and show it to them. Do not restate a card you have shown.
2. Check which model you are running on: your own instructions name it. Rubicon is tested on Opus at the default effort; Fable, the larger model, is just as suitable, so on Opus or Fable say nothing about the model. On a Haiku model, say that Rubicon needs a stronger model, that they can switch to Opus or Fable with `/model` (or the model menu in the Claude app) and type `/rubicon` again, and stop. On a Sonnet model, say in one sentence that Rubicon is meant for Opus or Fable and that on Sonnet the answer may miss passages, suggest switching the same way, and carry on only if they prefer to stay. If you cannot tell which model you are, say so and recommend Opus or Fable. Add once that a lower `/effort` setting than the default makes the reading less careful. Put any of these model notes in a line under the card, then end this first message by asking whether to begin with the documents, and wait for their answer before you read any document.
3. Check the tools the recount needs. Run `python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" --help` and `node --version`. If `python` is not found, try `python3` (a Mac has only `python3`) and use whichever works wherever these instructions say `python`. If a command is refused or blocked, by a permission setting or anything else, say that it was refused and ask the evaluator to allow it; do not guess at another cause. If something is missing, tell the evaluator in one sentence what it is, offer to install it, and do so once they agree: on Windows, Python with `winget install -e --id Python.Python.3.12` and Node.js with `winget install -e --id OpenJS.NodeJS.LTS`; on a Mac, Python with `xcode-select --install` and Node.js with `brew install node` if Homebrew is there, otherwise point them to nodejs.org; on Linux, including a cloud sandbox Claude runs in, with the system's package manager. After installing Python or Node.js on their own computer, ask them to quit and reopen the Claude app so it sees the new program, then type `/rubicon` again, and stop; in a sandbox, carry on once the check passes.
4. Find the documents. If they were attached to the conversation or added to a project rather than sitting in the folder you are working in, make a new folder in the place where you are allowed to write (or use the one you made earlier in this conversation), copy them into it, and work there from now on; "this folder" below means that one. `corpus/` in this folder holds the documents every question here is answered from: one plain-text file per document and `corpus/index.csv` with the columns `id`, `title` and `file`, plus a column for each fact about the documents, such as site or respondent type. If it does not exist, make it from the documents in this folder, leaving the originals untouched: convert Word, PDF or Markdown files to text, and say which files you could not read. If it exists, compare it with the documents in this folder and list any that are not in it yet; once the evaluator agrees, add them in the same way. Then ask once for the facts about any document that lacks them, from a spreadsheet they name or from the file names, saying in a sentence that a comparison between groups of documents can only use facts recorded here. Show the evaluator the list, with one specific observation about the documents that bears on the question, in a measured voice, such as how few documents a likely comparison would rest on; then ask them to confirm it before you go on.
5. Settle the question with the evaluator before anything is coded, as an experienced evaluator would with a client: one short exchange at a time, never a questionnaire. Read `${CLAUDE_PLUGIN_ROOT}/guidance/settling-the-question.md` first and settle it that way; it is written for Rubicon's own service, so leave aside what it says about `record/plan.md`, `skim.md` and the `mcp__rubicon` tools. When you suggest how to answer it, read the index of Rubicon's method notes, `${CLAUDE_PLUGIN_ROOT}/knowledge/README.md`, and open the pages that fit the question (process tracing, contribution analysis, QCA, realist evaluation, outcome harvesting, QuIP, Most Significant Change, the OECD-DAC criteria and the rest; `choosing-a-method.md` where the question names no method), so the approach you recommend follows them. If the evaluator names a method, or asks for the kind of claim one of these pages governs, read that method's main page and its page on Rubicon, if it has one, before saying how you would answer; follow it, say plainly where the question or the documents do not suit the method and what would serve instead, and name the method in the settled question so the brief reads the same pages; that is also where the skill's own `guidance/knowledge/` pages are. If the question asks how good something was (was it effective, good enough, relevant, sustainable, worth the money), read `${CLAUDE_PLUGIN_ROOT}/guidance/rubrics-and-verdicts.md` (with the same caveat) and `${CLAUDE_PLUGIN_ROOT}/knowledge/evaluative-rubrics.md` and help the evaluator settle the rubric now, before any document is read, since a standard set after seeing the evidence can be made to fit any of it: ask for one in their terms of reference or framework first; otherwise draft its criteria from the question and the evaluation notes, propose levels from best to worst each with a descriptor of what earns it in their words, and say how the criteria combine, offering thresholds as forms with the numbers left blank for them to fill. Write the rubric back and wait until they agree it; it is theirs, and the answer applies it as written. If they would rather not set one, say that the answer will stop at the table a verdict would read. When the verdict has real consequences (to fund, scale or stop something, or to judge it effective), or the evaluator asks to test the workflow first, read `${CLAUDE_PLUGIN_ROOT}/guidance/test-corpora.md` and offer what it describes: two small made-up corpora, one written to pass and one to fail, to show the workflow can tell them apart before it meets the real documents. Ask also what decision or report the answer will feed, and explain, a sentence each, the choices that change the run: answering from every document or from a sample first, that a longer corpus takes longer and uses more of their Claude plan, and that the run can stop at agreed points for people to take part: once the definitions are written and a few documents coded, so stakeholders can agree what each category means before everything is counted, and once the answer is drafted, before the report is made. A request such as "summarise these documents" or "what are the main themes" gets the same treatment: say why it cannot be checked as put and offer the analytical question underneath it. If the evaluator still wants a plain summary once they have heard why, do not run Rubicon: say that their ordinary Claude can summarise the documents directly, that Rubicon is for an answer in which every number and claim can be checked, and stop. Otherwise write the settled question back to them and wait for their go. Before carrying out the brief, check your model again as in step 2, since it can be changed during the conversation. In the brief below, the question is the settled one, not the words typed after the command, and it includes the agreed rubric word for word, if there is one.
6. Make a folder for this question inside this folder, named with a few words of the settled question, and work in it from now on: everything below, the brief included, happens there, so a second question never overwrites the first. Copy `corpus/` into it, so the run keeps the documents exactly as they were when it answered; copy `${CLAUDE_PLUGIN_ROOT}/contract/pieces.md` to `contract/pieces.md` in it, and the folder `${CLAUDE_PLUGIN_ROOT}/knowledge` to `knowledge/`.
7. Carry out the brief, stopping at any point agreed for people to take part: show the evaluator what is to be agreed in plain words (the definitions with an example passage for each, or the draft answer), wait, and carry on with their changes, recoding what the changes affect. When the recount's report is clear, have the coding and the answer read a second time, before a draft is shown to anyone. It takes two helpers that start fresh and never see your reasoning, such as subagents started with the Agent tool; say in a sentence that this second reading is what catches the errors one reader makes, and that it takes a while longer. First, the second coder: start one helper on Sonnet with the text of `${CLAUDE_PLUGIN_ROOT}/briefs/recode.md`, `{{documents}}` replaced by "all of them"; on a corpus too large for one helper, split the documents into batches, one helper each, each brief naming its own batch. When the rows are in `recode/coded/`, copy `workflow.json` and `corpus/` into `recode/`, run `python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" recode`, then `python "${CLAUDE_PLUGIN_ROOT}/engine/compare.py" . recode`, which writes `recode/disagreements.md`. Second, the check: start one helper on Opus, or Fable if you are running on it, with the text of `${CLAUDE_PLUGIN_ROOT}/briefs/check.md`, `{{question}}` replaced by the settled question. It rules on each disagreement, corrects the rows, the definitions and `answer.md`, recounts and writes `check.md`. Read `check.md` and tell the evaluator in a sentence or two what the check changed. If you cannot start a helper, do both yourself in that order, coding afresh into `recode/` before you look at `coded/` again, and say plainly that the second reading was done by the same reader and is weaker for it. Then you may add to `answer.md` up to two lines holding only `{{figure <tabulate step id>}}`, each where a chart would say more than a sentence; where the answer compares groups of documents, show that comparison as one of them, or, where its table has more than two columns, as a markdown table whose cells are the cell ids, which the report draws with every count clickable; with the sentence before it saying what the chart shows; a table of a column by a yes/no column draws as paired bars, a table of two nominal columns as a grid of counts, a table of one column as bars, and a table of a code step's two link ends (its `links`) as a causal map whose arrows are clickable. If `answer.md` does not open with a `# ` heading, add one of a few words naming what the question is about, such as `# Did the training help sales?`; the report shows it as its title, with the full question beneath. Change nothing else in the answer. Then run `python "${CLAUDE_PLUGIN_ROOT}/engine/render_report.py" . --date "<today's date, such as 6 October 2026>"`. If it prints figure lines it left out, correct those lines as it says and run it again. It writes three files named from the question and the date, which it prints: the report (`.html`), the same report for Word (`.doc`) and the whole run in one file (`.zip`). Hand the three over so that each opens with one click, the report first, the way your environment gives files to the user: where it has an outputs folder, as Cowork and a chat with file creation do, copy them there (by way of a temporary folder if copying straight in fails) and present them with whatever it offers for that, such as a file link or a tool that shows files; where the user opened the folder you are working in, link the files there. Never leave them as names in code formatting that the user cannot click. Then tell the evaluator, by those names:
    - the report is to open in their browser (or show it to them yourself if you are running somewhere they cannot open it); every number and every quotation in it can be clicked to see what it rests on, and the browser's Print saves it as a PDF;
    - the `.doc` is the same report for Word;
    - the `.zip` is the whole run in one file, to keep or to pass on; because it holds their documents, it should be shared only with people allowed to read them;
    - the report is a draft to make sense of with the people it concerns, such as programme staff and participants, before it is final; offer to revise it with what they say;
    - `work/` holds the audit trail, and `workflow.json` with `coded/` the workflow that recounts it.

The brief:

An evaluator asks: "$ARGUMENTS" The documents are in corpus/ (corpus/index.csv lists them with their metadata). Answer the question, and write your answer to answer.md. Work however you judge best.

Method notes are in knowledge/ (knowledge/README.md lists them); consult any that bear on the question.

As you work, keep an analyst's audit trail in work/, so that a reviewer can check the answer and another analyst can follow the same procedure:
- every script you write, and its output;
- a table recording, for each document, what it contains that bears on the question, with the quotation;
- if you use subagents, the full brief you give each one and what it returned.
When you finish, write work/procedure.md: which documents were read, by whom, under which brief, and how the results were combined into the answer, pointing to the files above. It states the procedure only, not the findings.
Your work must also be left as a workflow that code can carry out again, so that every count in your answer is recounted by code from the rows you coded, and another coder can follow your definitions and code the documents afresh. contract/pieces.md describes the steps such a workflow is written in. Use only sample, code, tabulate and judge steps: you do the grouping yourself, so the categories you settle on become the values of nominal columns, or binary columns, each defined as the file asks. Leave out the settings that choose models, second coders and sections; you are the coder.
- Write workflow.json: {"question_as_agreed", "steps": [...]}, with a write step last, {"id": "answer", "kind": "write", "inputs": [the tabulate and judge steps, and the code steps whose rows you cite]}.
- For each code step, write coded/<step id>.json: a JSON list of the rows you coded, each {"document": its id in corpus/index.csv, "quote": the passage copied exactly from the document, and a value for each of the step's columns}. A per_document step has one row per document.
- Run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . This recounts your workflow from your rows, writes recount/tables.md (every cell with its id) and recount/rows.md (every row with its id), and lists in recount/report.json what it could not use: quotations not found in their document, values not among a column's defined values, faults in the workflow. Fix what it reports and run it again until the report is clear.
- In answer.md, write every count as its cell's id in braces, such as {t_base.c1}, which code replaces with "n of base"; do not write numbers yourself. Cite the rows a claim rests on by their ids in square brackets, as recount/rows.md gives them. Quote documents exactly.
- Then run: python "${CLAUDE_PLUGIN_ROOT}/engine/recount.py" . --answer answer.md and fix what its "answer" section reports. recount/answer.resolved.md is the answer the evaluator reads.
